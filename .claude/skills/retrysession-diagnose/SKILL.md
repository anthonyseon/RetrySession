# RetrySession 이 안 돌 때

**증상 하나에 원인이 여럿이고, 대처가 서로 다르다.** 먼저 가르고 나서 고쳐라.
추측으로 재등록하거나 재시작하면 멀쩡한 것을 부수고 진짜 원인을 덮는다.

## 먼저 — 한 번에 전부 본다

```powershell
.\start.exe -Status
```

여기서 네 가지가 각각 나온다. **하나만 보고 판단하지 마라.**

| 나오는 것 | 뜻 |
|---|---|
| scheduled tasks | 예약이 **등록**돼 있나 · 마지막 결과 |
| actually running | 서버가 **응답**하나 · 트레이가 살아 있나 |
| record freshness | **기록**이 신선한가 (fail-closed) |
| resume budget | 재시작 예산·차단 상태 |

## 증상 1 — 감시 기록이 안 남는다

원인이 둘이고 대처가 반대다. **이 구별이 이 프로젝트의 핵심 교훈이다.**

| 예약 등록 | 기록 | 원인 | 대처 |
|---|---|---|---|
| 있음 | 낡음 | 작업은 도는데 **실패**하고 있다 | 로그·결과 코드를 읽는다 |
| 없음 | 낡음 | 작업 자체가 **사라졌다** | 재등록한다 |

```powershell
# 결과 코드를 뜻으로 읽는다 (267009=실행 중, 267011=아직 실행 안 됨, 0xC000013A=중지됨)
.\start.exe -Status
```

```bash
# 실패하고 있다면 여기에 이유가 있다
cat state/sessions/<sessionId>/heartbeat.log | tail -20
```

감시 대상이 **하나도 없으면** 기록이 없는 게 정상이다:

```bash
npm run list        # 대상 목록. 비어 있으면 화면에서 세션을 골라 켜라
```

## 증상 2 — 재시작이 돌지 않는다

**대부분 정상이다.** 가드에 막힌 것은 실패가 아니다.

🔴 **먼저 화면을 봐라.** 세션 줄의 배지가 `재시작 켬 · 대기 (작업중)` 처럼 **무엇이
막는지 한 단어**로 말한다(배지에 마우스를 올리면 자세한 이유, 상세의 **재시작 로그**
탭 맨 위에는 판정 패널과 고치는 단추). 화면과 재개는 **같은 판정**
(`lib/resume-gate.mjs`)을 쓰므로 둘이 다를 수 없다 — 다르면 그게 결함이다.

`재시작 꺼짐` 이면 스위치가 안 켜진 것이고, `재시작 켬 · …` 이면 켜진 것이다.
스위치는 **테두리 색**으로도 갈린다 — 켬은 강조색 테두리·왼쪽 띠, 꺼짐은 점선+흐린 글자.
누른 결과는 동작줄 오른쪽에 적힌다(`✖` 로 시작하면 적용되지 **않았다**).

### 🔴 '지금 재시작 실행' 을 눌렀는데 아무 일도 없다 — **로그보다 동작줄을 먼저 읽어라**

🔴 **이 단추는 `--now` 다 — 재시작 조건을 전부 건너뛴다**(사용자 결정 2026-09-28).
그래서 아래 «흔한 이유» 들은 **예약 회차**의 것이다. 단추를 눌렀는데 안 돌았다면 남은
이유는 셋뿐이다 — 띄울 자리가 없다(작업 디렉터리) · 보낼 말이 없다(재개지시) ·
이미 재개가 돌고 있다(세션 락·단일 실행).

서버는 띄우기 **전에** `resume.mjs --dry-run --now` 로 다시 판정하고, 막히면 **띄우지 않고**
그 이유를 응답에 담는다. 화면은 그것을 동작줄에 적는다:

- `강제 실행 — 조건을 건너뛰고 띄웠습니다: …` → 실제로 떴다. 진행은 재시작 로그에서 본다.
- `띄우지 못했습니다: <이유>` → **띄우지 않았다.** 그 이유가 곧 답이다(위 셋 중 하나다).
- `🔴 화면이 보여주던 판정과 달랐습니다` → 화면이 몇 초 묵어 있었다는 뜻이다(자동갱신을
  껐거나 창을 오래 열어 뒀을 때). 화면은 그 자리에서 다시 읽는다.

로그에 아무 줄도 안 늘었다면 **띄우지 않은 것**이지 조용히 실패한 것이 아니다.

명령으로 보려면:

```bash
npm run resume:dry      # 가드 판정 + 넘길 지시문까지 보여준다
npm run resume:status   # 예산·연속실패·차단·과부하 횟수
```

흔한 이유와 뜻 (괄호는 배지의 단어):

- `도구 N개가 결과를 기다리는 중이다` / `마지막 차례가 사람이다` / `도구 결과가 막 돌아왔다`
  (작업중) — 그 세션이 **일하는 중**이다. 끝나고 3분 조용해지면 대상이 된다.
  🔴 셋의 **기다리는 창이 다르다**: 도구 결과는 5분, 사람의 질문은 회차 시간(`timeoutMin`)까지.
  도구 결과가 기록에 `user` 로 들어오는 탓에 예전에는 잘린 회차의 마지막 결과를 「사람 차례」로
  읽어 30분을 막았다(실측 09-28: kill 뒤 다음 회차가 정확히 30.1분 뒤).
  🔴 **`세션이 실행 중이다 (pid ...)` 는 더 이상 막는 이유가 아니다.** 로그에 그 줄이 수백 번
  이어져 있다면 옛 버전이다(실측 `SKIP ×539` + `×21`) — pid 를 "사람이 쓰는 중"으로 읽어
  제한 해제 재개가 통째로 막혀 있었다. 지금은 기록으로 판정한다(Manual §5-1).
- `마지막 활동 시각을 알 수 없다` (확인불가) — 모르면 막는다. 트랜스크립트를 읽을 수 있는지 본다.
- `방금까지 활동이 있었다` (활동중) — 아직 사람이 붙어 있을 수 있다
- `할 일이 없다 (n/n 전부 done)` (할일없음) — 추적기가 끝났다
- `추적기도 재개지시도 없다` (지시없음) — 무엇을 이어서 할지 정해지지 않았다. 상세 → 설정 탭에서 재개지시를 넣어라.
- `이 저장소는 자율 재개가 꺼져 있다` (저장소잠금) — `config/projects.json` 의 `resume.enabled`. `--force` 로도 안 뚫린다.
- `오늘 N회 실행 (하루 상한 12회)` (상한도달) — 횟수만 막는다. **비용은 막지 않는다**(통계·참고선)
- `마지막 실행 N분 전 (최소 간격 30분)` (상한도달) — 기다린다
- `회로 차단됨` (연속실패) — 원인을 고친 뒤 `npm run resume:rearm` 또는 판정 패널의 [차단 해제].
  🔴 **성공 한 번이 차단을 푼다**(2026-09-29부터) — 사람이 `지금 재시작 실행` 으로 돌려 `ok` 로
  끝나면 그 회차가 푼다. 로그가 `연속 0회 실패로 회로 차단됨` 이라 적혀 있으면 **옛 버전**이다
  (성공이 연속실패를 0 으로 되돌린 뒤에도 차단이 남아 있던 결함이다).
- `끊긴 응답을 이미 한 번 이어 봤는데 또 끊겼다` (반복끊김) — 원인이 절전이 아니다. 재개지시로 방향을 바꿔라.

로그에 같은 이유가 이어지면 `SKIP ×4 (처음 …)` 로 **접혀서** 쌓인다 — 줄이 안 늘어난다고
안 도는 것이 아니다.

**`limited`·`auth`·`overload` 로 끝난 회차는 실패가 아니다.** 사용량 제한 · 로그인 끊김 ·
API 과부하(529·5xx)는 연속실패로 세지 않는다 — 기다리면 풀린다.
차단하지 않는 대신 **세어서 말한다**: 과부하는 하루 3회를 넘으면, 인증은 **한 번만 있어도**
(마지막 회차가 그것이면) 경보로 올라온다. 세션 배지에도 `과부하 N회`·`로그인끊김 N회` 로 남는다.

> 🔴 `RUN 끝 · fail` 인데 요약이 `Failed to authenticate…` 라면 **옛 버전이 남긴 기록**이다.
>   지금은 `auth` 로 갈린다(`classify.classifyRun`). 그 회차가 올린 연속실패는 실제 고장이
>   아니므로 [차단 해제] 로 풀어도 된다.

### 🔴 `timeout · $0 · 턴 ?` 이 이어진다 — **멈춘 것이 아니라 잘린 것일 수 있다**

`--output-format json` 은 끝에 한 번만 출력하므로, kill 당한 회차는 비용·턴·요약이 사라진다.
**`$0` 을 «일을 안 했다» 로 읽지 마라.** 그 회차가 무엇을 했는지는 트랜스크립트가 안다:

```bash
npm run resume:status          # 「시간초과 N회」 — 오늘 몇 번 잘렸나
```

kill 시각 **직전**의 엔트리를 보면 갈린다 — 도구가 초 단위로 돌고 있었다면 일하는 중에 잘린
것이다(실측 09-28: 세 회차가 도구 56·58·75회를 돌리고 성공 회차의 1.5~3배를 태웠는데 기록은
`$0` 이었다). 그러면 고칠 것은 회차가 아니라 **크기**다 — `timeoutMin` 을 올리거나 재개지시를
쪼갠다. 지금은 타임아웃을 실패로 세지 않고(회로를 태우지 않는다) 하루 2회부터 경보로 올리며,
결과 JSON 이 없으면 비용을 **트랜스크립트에서 재어** `$12.34 (트랜스크립트 실측)` 처럼 적는다.

### 증상 2-2 — `RUN 끝 · ok` 인데 **아무것도 남지 않았다** (권한거부 N건)

실측으로 두 번 겪었다: `ok · $18.271 · 권한거부 11건` · `ok · $15.814 · 권한거부 7건` —
둘 다 디스크 변경 **0건**이었다. 결과가 `ok` 인 것은 프로세스가 정상 종료했다는 뜻일 뿐이다.

```powershell
# 그 회차가 무엇을 쓸 수 있었는지 — 로그의 이 두 줄부터 본다
Select-String -Path state\sessions\<세션id>\resume.log -Pattern 'cwd |--add-dir'
```

| 보이는 것 | 뜻 |
|---|---|
| `cwd` 가 고치려는 파일의 저장소가 **아니다** | 그 파일이 작업 폴더 밖이라 쓰기가 승인 대기가 된다. 뿌리는 추적기를 소유한 저장소여야 한다(`launchRoots`) |
| `--add-dir (없음)` 인데 세션이 여러 곳을 오갔다 | 다른 폴더를 못 쓴다 |
| 둘 다 맞는데도 거부된다 | **그 저장소의 규약** 문제다. 권한 자체는 `--dangerously-skip-permissions` 와 같으므로(설정 `permissionMode: bypassPermissions`) 승인으로 막히지 않는다 |

🔴 지시문은 그 저장소의 `.claude/skills/*`·`CLAUDE.md`·`README.md` 를 먼저 읽고 따르라고
말한다. 무인 실행이 "규약 때문에 멈췄다"고 적었다면 그것은 **정상 동작**이다 —
권한을 더 열 것이 아니라 그 규약이 요구하는 것(스크립트·게이트)을 갖춰 줘야 한다.

### 증상 2-1 — 재개가 **몇 초 만에** 끝난다 / 로그인 경보가 떴다

실측(2026-09-28): 첫 실제 자율 재개가 `RUN 끝 · fail · 5초 · $0 · 턴 1 · exit 1` 로 끝났고
요약은 `Failed to authenticate: OAuth session expired and could not be refreshed` 였다.
**5초는 일을 한 시간이 아니다** — 붙기도 전에 튕긴 것이다.

```powershell
claude auth status --json     # loggedIn 이 정답이다. 화면 머리의 계정 글자도 이것을 읽는다
```

경보 문구로 원인이 갈린다. **대처가 다르다:**

| 경보 | 뜻 | 대처 |
|---|---|---|
| 🔴 **로그인이 끊겼습니다** | 조회가 성공했고 «로그인 안 됨»이라 답했다 — 확실하다 | VS Code 에서 다시 로그인 |
| 🟡 **로그인 상태를 확인할 수 없습니다** | 조회 **자체**가 실패했다(타임아웃·CLI 없음) — 모른다 | 한 번 더 본다. 계속 뜨면 위와 같이 |
| 🟡 **로그인이 끊겨 재시작이 헛돌았습니다** | 오늘 `auth` 로 끝난 회차가 있고 마지막이 그것이다 | 대개 저절로 낫는다(토큰 갱신). 다음 회차를 기다린다 |

차단되지 않았으므로 `--rearm` 은 필요 없다. 로그인이 살아나면 다음 회차가 저절로 돈다 —
**API 키는 쓰지 않는다**(CLAUDE.md §6). 그래서 이 계정이 없으면 재개는 한 번도 못 돈다.

## 증상 3 — 화면이 안 열린다 / 트레이가 없다

```powershell
.\start.exe                 # 서버·트레이를 확인하고 창을 연다
```

그래도 안 되면 순서대로:

```powershell
# 1) 서버가 응답하나
curl http://127.0.0.1:7345/api/tray

# 2) 포트를 누가 잡고 있나 (낡은 프로세스가 잡고 있으면 새 서버가 EADDRINUSE 로 죽는다)
Get-NetTCPConnection -LocalPort 7345 -State Listen | Select OwningProcess

# 3) 재등록 — 포트를 먼저 비우고 응답까지 확인한다
.\scripts\register-ui.ps1
```

**트레이 아이콘이 안 보이면** 숨겨진 것일 수 있다(Windows 11 기본).
설정 > 개인 설정 > 작업 표시줄 > 기타 시스템 트레이 아이콘. `register-tray.ps1` 이
고정을 시도하지만 실패할 수 있다.

트레이가 *실행 중인지*는 뮤텍스로 판정한다. 명령행 매칭은 거짓 양성이 난다
(진단 명령 자신이 `tray.ps1` 문자열을 포함해 걸린다).

### 증상 3-1 — 상태 창이 **여러 개** 열린다

```powershell
.\scripts\open-app.ps1 -NoWait   # "already open - brought it to the front." 라고 해야 정상
```

🔴 **프로세스를 세지 마라.** Chromium 은 같은 프로필에서 브라우저 프로세스를
재사용하므로 창이 셋이어도 pid 는 1~2개다 — 실측으로 이 함정에 두 번 빠졌다.
창을 세려면 `open-app.ps1` 의 `Get-AppWindows` 와 같은 방식(`EnumWindows` +
보이는·제목 있는 `Chrome_WidgetWin_1`)을 써야 한다.

중복이 생겼다면 보통 **경합**이다: 클릭마다 새 powershell 이 뜨고 그것이 `Add-Type`
컴파일을 끝내기까지 초 단위가 걸려, 그 틈의 클릭들이 모두 "창 없음"을 본다.
지금은 두 겹으로 막혀 있다 — `state/locks/open-app.lock`(배타 열기) 과
**띄운 뒤 남는 창 정리**. 둘 중 뒤쪽이 실제 보증이므로, 중복이 다시 보이면
사후 정리가 도는지부터 확인하라(`-KeepExtra` 로 끄고 들여다볼 수 있다).

## 증상 4 — 세션이 목록에 없다

**열린 폴더와 세션은 다른 것이다.** 순서대로 가려라:

1. **화면의 "열린 폴더" 줄** — `여기서 시작한 세션 없음` 이면 그 폴더에서 Claude Code 를
   시작한 적이 없다는 뜻이다. 빠뜨린 게 아니다.
2. **목록 끝의 "짝지어지지 않은 claude 프로세스"** — CLI 가 모르는 프로세스도 여기 나온다.
3. 그래도 없으면 프로세스를 직접 본다:

```powershell
Get-CimInstance Win32_Process -Filter "Name='claude.exe'" |
  Select-Object ProcessId, CommandLine | Format-List
```

명령행에서 갈린다:
- `--claude-in-chrome-mcp` → **보조 프로세스**, 세션이 아니다
- `--add-dir <폴더>` → 그 폴더는 **덧붙인 폴더**이지 세션의 시작 위치가 아니다
- `--resume=<id>` → 이어받은 세션 id

실측 사례: `claude agents --json` 이 세션 2개를 보고할 때 실제 `claude.exe` 는 4개였다.

## 증상 5 — 콘솔 창이 뜬다

예약 작업의 action 이 `node.exe` 를 직접 부르고 있다. `-Hidden` 설정은 소용없다
(그건 작업 스케줄러 목록에서 작업을 숨기는 옵션이다).

```powershell
# action 확인 — runhidden.exe 를 거쳐야 한다
(Get-ScheduledTask -TaskName 'EasyAI-RetrySession-UI').Actions[0].Execute

# 고치기
.\scripts\build-exe.ps1      # runhidden.exe 가 없으면 만든다
.\scripts\register-ui.ps1    # 감시·재시작도 같은 방식으로 재등록
```

## 증상 6 — 예약 작업이 실패로 남는다

결과 코드를 먼저 뜻으로 읽어라. **실패가 아닌 것들이 있다:**

| 코드 | 뜻 |
|---|---|
| `0` | 성공 |
| `267009` | 실행 중 (서버·트레이는 이게 정상이다) |
| `267011` | 아직 실행되지 않음 |
| `0xC000013A` | 중지 신호로 종료 (`Stop-ScheduledTask` 등) |
| `2` | 우리 쪽에서는 보통 **포트 충돌** |

🔴 **`start.exe -Restart` 직후 1~2분은 예약 경보를 믿지 마라.** 강제 종료 결과(-1)가
다음 회차까지 남아 «예약 작업이 멈춰 있습니다» 로 보인다. 실측(2026-09-28): 재시작
직후 트레이가 그렇게 떴고, 트레이는 실제로 돌고 있었으며, 다음 회차에 저절로 사라졌다.
**자기 자신의 정상 절차를 고장으로 읽는 것**이라 이미 한 번 고친 부류다.

낡은 결과가 남아 경보로 보일 수 있다. 한 번 돌려보고 다시 확인하라:

```powershell
Start-ScheduledTask -TaskName 'EasyAI-RetrySession-Heartbeat'
Start-Sleep 12
(Get-ScheduledTaskInfo -TaskName 'EasyAI-RetrySession-Heartbeat').LastTaskResult
```

🔴 `Stop-ScheduledTask` 직후 `Start-ScheduledTask` 는 먹지 않는 경우가 있다
(상태가 Ready 로 남고 `0xC000013A` 로 끝난다). **재등록이 확실한 복구 경로다.**

## 증상 7 — 고쳤는데 반영이 안 된다

살아 있는 node 프로세스는 기동 시점의 모듈을 들고 있다.

```powershell
.\start.exe -Restart
```

## 증상 8 — "이미 돌고 있다" 며 건너뛴다

정상이다. 중복 실행은 막혀 있고, 그래서 `exit 0` 이다.

진짜로 아무것도 안 도는데 이 메시지가 나오면 **유령 락**이다.
락은 pid 생존과 시간 한계를 둘 다 보므로 보통 스스로 회수하지만, 확인하려면:

```bash
ls state/locks/ && cat state/locks/*.lock
```

`pid` 가 죽어 있으면 다음 실행이 회수한다. 급하면 해당 `.lock` 을 지워도 된다 —
다만 **정말로 안 돌고 있는지 먼저 확인**하라. 도는 것을 지우면 중복이 생긴다.

## 마지막 수단 — 전부 다시 세운다

```powershell
.\start.exe -Uninstall      # 예약 전부 해제 (state\ 는 남는다)
.\scripts\build-exe.ps1
.\start.exe -Install        # 다시 등록 (재시작까지 원하면 -WithResume)
```

`state/` 는 지워지지 않으므로 감시 대상·이력·예산이 그대로 돌아온다.
